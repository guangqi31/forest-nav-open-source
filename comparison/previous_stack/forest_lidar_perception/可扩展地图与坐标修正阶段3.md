# 第3步：LIO地形代价图、自动扩展与坐标修正

后续第4步已完成接管，森林主入口默认LIO，见[LIO接管Nav2阶段4.md](LIO接管Nav2阶段4.md)。本文以下保留第3步当时的旁路接入与验证范围。

2026-11-13。本阶段已接入并做有限验证；LIO新地图暂时独立输出，当前Nav2仍沿用原定位和地图入口。没有训练或修改机器人策略。

## 当前链路与启动

原始激光/IMU → FAST-LIO → 估计配准点云与激光位姿 → 独立原版CMU terrain_analysis → 地形观测证据 → 全局/局部二维代价图。

```bash
/home/ubuntu/robot_projects/forest_nav/forest_lidar_perception/start_lio_mapping.sh
```

这个入口现在会同时启动LIO地形分析和代价图，无需另起多个终端。默认G1零目标速度，等待初始化后出图。已有传感器运行时仍可用start_lio.sh单独接入，ROS_DOMAIN_ID必须一致。独立入口默认域191，原导航入口默认域186。

新增接口：

| 接口 | 内容 |
|---|---|
| /lio/lidar_odometry | 从估计IMU位姿及真实安装外参计算激光位姿，供CMU使用 |
| /lio/terrain_map | CMU相对地面高度差点云，lio_odom连续坐标 |
| /lio/traversability_map | 全局OccupancyGrid，lio_map坐标，历史观测保留 |
| /lio/traversability_map_local | 最近3秒观测，过期恢复未知 |
| /lio/mapping_status | 会话、修正版本、重置代次、边界、已知单元数和错误 |
| /lio/mapping/correction | std_msgs/String，JSON v1绝对平面坐标修正 |
| /lio/mapping/save | std_srvs/Trigger，保存代价图与源观测证据 |

TF结构为lio_map→lio_odom→lio_imu→lio_lidar。lio_map初始与lio_odom重合，原点来自LIO初始化，不自动等于USD的世界原点。原map→odom→base_link导航分支保留。

独立CMU只消费/lio/cloud_registered和/lio/lidar_odometry。上游源码硬编码输出frame_id=map；专用桥根据本实例的实际输入将其明确标记为lio_odom。没有把原真值/terrain_map混入新链路，也没有修改上游CMU或FAST-LIO源码。

## 地图如何扩展

分辨率仍为0.2m；初始32×32m。有实际观测越过当前边界时按整格添加未知边框，历史格子做整数索引搬运，世界坐标和分辨率保持不变。-1未知、0..99地形代价、100禁行的编码不变。

当前存储上限256×256m，源坐标也限定在初始原点附近256m范围；最大200万个缓存测量点。超过限制明确拒收并保留已有地图，不裁掉后宣称完整、不降低分辨率、不静默删除历史。这是有边界的工程实现，不是无限地图。

原导航正在使用的TerrainCostmap也已启用同样的自动边界扩展；只改变几何容量，不切换定位，不改未知/时效保护。Nav2使用全量OccupancyGrid，原生StaticLayer会根据尺寸、分辨率和原点重新调整栅格，无需另写Nav2地图插件。

扩图由观测驱动。当前公共目标入口对“尚在当前地图边界之外”的目标仍会拒绝；本阶段没有把此类目标直接放行为穿越未知。以后接管导航时仍需统一远目标探索接纳策略。

## 坐标修正如何避免重影

源观测证据始终保存于连续lio_odom中。每个0.2m源单元保留最近一次观测的全部实际点、相对高度和时间，而非仅保存一张已栅格化图片。

修正后从这些实际坐标重新投影、重新落格并构建两张候选地图。两张都成功才替换内存中的公开地图状态；旧位置不会残留一份障碍，新观测也先经过同一变换再进入地图。同一目标格选择最近观测，同一时刻取最大代价。没有旋转旧栅格图片、插值出自由区域或用真值补图。

本阶段支持的修正为绝对[x米,y米,yaw弧度]：p_lio_map=R(yaw)×p_lio_odom+t。它改变全局地图坐标，不改变FAST-LIO内部连续状态。暂不支持滚转/俯仰修正或非刚性的逐关键帧位姿图变形；这些需要重新做地面分析或引入真正的后端优化。

直接使用客户端，例如将当前独立地图设置为绝对平移(2,3)m、偏航10度：

```bash
/home/ubuntu/robot_projects/forest_nav/forest_lidar_perception/correct_lio_map.sh --x 2 --y 3 --yaw-deg 10
```

恢复单位变换：

```bash
/home/ubuntu/robot_projects/forest_nav/forest_lidar_perception/correct_lio_map.sh --x 0 --y 0 --yaw-deg 0
```

这是地图坐标设置，不是移动机器人指令。客户端读取当前会话和修正版本，提交唯一request_id，等对应确认；不是每运行一次就再累加一次平移。

底层JSON契约：

```json
{
  "schema_version": 1,
  "request_id": "调用方生成的唯一标识",
  "session": "从/lio/mapping_status.source[0]读取",
  "clock_epoch": 0,
  "base_revision": 0,
  "revision": 1,
  "frame_id": "lio_map",
  "child_frame_id": "lio_odom",
  "map_to_odom": [2.0, 3.0, 0.1745329252]
}
```

会话、坐标系或基础版本不匹配、修正版本不递增、非有限数、超范围请求均拒绝，保留原图/TF/版本。成功后correction_revision更新，reset_generation递增，供后续导航取消旧坐标目标。内存状态提交不等于多个ROS话题之间具备数据库事务；第4步接入任务控制时仍需用代次与ready门控处理修正过渡。

这里只接好了修正消费接口，没有自动产生修正的回环/全局优化器。FAST-LIO短程定位误差不会因为这个接口存在而自动消失。

## 验证结果与范围

1. 真实Isaac+G1站立采集：results/lio_20261113_192943/。50个LIO输出、约9.8秒仿真记录；新链路更新48次，全局1158个已知单元、局部1152个，成功保存地图及观测证据。未发送运动目标，不能将站立毫米级漂移当作行走精度。
2. 受控ROS输入与项目实际使用的原生planner_server：results/mapping_stage3_ros/verification.json。地图从160×160扩至240×240（32m→48m），旧障碍世界位置保持、边框未知；平移修正后旧位置恢复未知，新位置有障碍；后续地面观测正确清除新位置障碍；客户端可确认修正；生命周期正常清理、进程退出码0。输入为接口检查用测量，不是假称机器人实际走到20m处。
3. 34项针对性回归通过，覆盖原地图生命周期、时钟/坏帧保护、激光IMU契约，以及扩图、修正和缓存上限。

真实采集后的退出流程发现第二次SIGINT可能打断保存，已补退出归档期间忽略重复SIGINT；此小修改没有再次跑物理仿真。独立costmap示例进程退出异常通过改用实际planner_server和正常生命周期清理完成了接口复核。

结果目录的costmaps/global.npz、local.npz包含坐标、边界、观测时间、会话、修正和代次；evidence.npz保存lio_odom源测量，便于审计。本阶段不自动加载别的定位会话。
